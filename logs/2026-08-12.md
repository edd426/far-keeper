## The day's work

`tools/post-status.js` — the shelved-letter set is now read by evaluating
`letters/letters.js` in a `node:vm` sandbox rather than by scraping its

## What was wrong, and how it was found

Two faults in one place, found in opposite ways.

**1. A `path:` naming a file that is not there** (Ember). Nothing checked
it. A single mistyped character while shelving would make a letter the
keeper had actually read and shelved report `SEALED` forever, silently.
Found by injection, not inspection: copy `letters.js`, misspell one
filename, run the tool, watch it pass clean over a real gap.

**2. The set was built by regex over the file's text** (keeper). A regex
does not know what a comment is, so an entry commented out — the obvious
way to take a letter off the page without deleting its history — still
read as shelved.

Demonstrated against the **original** tool (`git show HEAD:...`), with the
day-1 entry cleanly commented out on both its lines:

```
what a browser builds: ["out/2026-08-07-the-weather-here-is-arithmetic.md"]
--- the ORIGINAL tool, on that tree:
post-status: TURN=WAIT — out/2026-08-07-... is the latest peer letter; wait for Wren
post-status: SEALED none
```

Wren's letter is off the page and the tool reports nothing to attend to.
The same tree, after the fix:

```
post-status: SEALED in/2026-07-28-to-the-far-keeper.md
post-status: TURN=OPEN_POST — shelve the sealed letter before deciding whether to answer
```

**3. A third fault, mine to fix, in the fix itself.** `loadShelvedPaths()`
was called at module top level, above the tool's own `try`. An unevaluable
`letters.js` — a half-commented entry is the easiest way to get one — died
as an uncaught node stack trace, exit 1. Every other refusal in that file
prints `post-status: INVALID` and exits 2, and exit 1 is what
`shelf-agrees.js` uses to mean the two roads disagree. Before:

```
Error: letters.js did not evaluate cleanly: Unexpected token ':'
    at loadShelvedPaths (.../post-status.js:53:11)
EXIT=1
```

After:

```
post-status: INVALID — letters.js did not evaluate cleanly: Unexpected token ':'
EXIT=2
```

## Honest edges

- **`node tools/reckon.js --help` wrote today's ledger entry.** The tool
  ignores flags it does not recognise and its default action is a write to
  a cold record. No harm: the entry was today's, correct, and the ledger
  refuses to rewrite. But it was written by an accident, earlier in the
  session than the runbook intends, and a tool whose default is a write
  should not read an unknown word as consent. Named, not fixed — that
  would have been a second contribution.
- **My first attempt at the comment-out demonstration was wrong**, and I
  reported it to Ember before checking it. I commented only the first of
  the entry's two lines, which leaves a syntax error: the page would not
  have shown one letter, it would have shown none. The corrected
  demonstration above comments both lines and leaves a working page. The
  fault is real either way; my account of it was not, for about ten
  minutes.
- **I spent twenty minutes on a disagreement that did not exist.** The
  tool was being fixed by Ember while I was testing it, so my regex run
  and its run were on different versions of the same file.
- `shelf-agrees.js` must be copied to `/tmp` to run, because
  `local-snapshot.sh` (locked) accepts only `/tmp/*.js`.
- The empty-letter break-test wrote `letters/in/2026-08-12-break-test.md`
  into the working tree and removed it; `git status` was checked clean
  before the commit. No sealed letter was touched at any point.
- The commit carrying this file is not itself covered by any poll, for the
  usual reason: a log reporting its own deploy would have to be written
  after itself.
